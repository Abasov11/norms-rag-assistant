# RAG-ассистент по нормативной базе — инженер задаёт вопрос вместо поиска по 400 PDF

> **Портфолио-кейс.** Это витрина инженерного решения: архитектура, ключевые
> решения и подобранные фрагменты кода. Это не полная рабочая сборка —
> рабочий код, ключи и данные заказчика сюда не входят.

## Задача

Инженер-проектировщик держит в голове (или ищет вручную по PDF) требования из десятков
строительных норм: СП, СН, ГОСТ и серии еврокодов EN. Вопрос вида «на какую высоту
рассчитывать ограждение кровли» требует найти нужный документ, нужный пункт и не перепутать
его с похожим пунктом соседней нормы на ту же тему — а в базе таких «близнецов» много: СН и
СП на один и тот же предмет разных лет, разные части одного еврокода.

**Цель системы:** чат-интерфейс (Telegram) поверх RAG по нормативному корпусу, который
отвечает со ссылкой «документ → пункт → страница» и **не отвечает вообще**, если основания
недостаточно — вместо того чтобы правдоподобно придумать число.

## Главный инженерный вызов: заземление в корпусе из сотен документов

Классический RAG «нашли похожий фрагмент → модель его пересказала» не проходит здесь по
одной причине: **номер пункта не уникален в корпусе.** «Пункт 5.2» есть почти в каждом
документе, поэтому сверить цитату ответа с источником по номеру пункта глобально нельзя —
нужно однозначно знать, из какого именно документа она взята.

Решение — заземление тегами, а не текстом:

1. Каждый найденный фрагмент при формировании контекста получает тег `[И1]…[Иn]`.
2. Модель обязана ссылаться на источник только тегом; инструкция в промпте прямо запрещает
   опираться на что-либо вне блока «ИСТОЧНИКИ».
3. Код проверяет: любой тег вне диапазона `1..n` — «выдуманная ссылка», ответ помечается как
   не прошедший проверку. Это не «промпт просит не выдумывать» — сослаться на несуществующий
   источник **технически невозможно**, потому что модель работает только с пронумерованным
   списком, а не со свободным текстом корпуса.
4. Отдельный слой (`entailment.py`) сверяет **числа и единицы** внутри уже процитированных
   утверждений с текстом источника — тег может быть верным, а величина внутри абзаца
   подменённой; эта проверка детерминированная (без LLM) и не зависит от доступности судьи.
5. Отказ («НЕДОСТАТОЧНО ОСНОВАНИЙ») засчитывается только если система **начинает** с этой
   формулы, а не если она где-то встретилась — иначе отказ с объяснением через смежные нормы
   ошибочно считался ответом. Смена правила на живом прогоне подняла корректный отказ по 15
   вопросам вне корпуса с 2/15 до 14/15 верных отказов.

См. [`snippets/citation_guard.py`](snippets/citation_guard.py) и
[`snippets/entailment_check.py`](snippets/entailment_check.py).

## Ещё инженерные решения

- **Гибридный поиск, вес лексики — по замеру, не по интуиции.** Вектор + BM25 + label-дорожка
  (прямая ссылка на номер пункта), слитые Reciprocal Rank Fusion. Равный вес лексической
  дорожки на эвал-наборе **роняет** recall (69/85 против 81/85 у вектора с малым весом
  лексики) — OR по лексемам тащит шум и вытесняет векторных кандидатов при слиянии. Вес 0.5
  выбран как нейтральная страховка под точные термины и номера, а не как «равноправная
  половина гибрида». См. [`snippets/hybrid_search.py`](snippets/hybrid_search.py).
- **LLM-реранк — второй этап после recall.** Гибридный поиск даёт широкий пул кандидатов,
  лёгкая модель (AUX-тир) выбирает из него точный топ; есть режим предварительного отбора
  документов (при большом пуле сначала выбираются 3-5 документов-кандидатов, потом чанки
  внутри них) — против «близнецов» одной темы в разных нормах.
- **Соседние пункты — отдельными источниками, не подклейкой текста.** Разбор частично
  неверных ответов показал: система находит верный пункт, но теряет условие или продолжение
  перечня в соседнем пункте того же подраздела. Соседи добавляются как самостоятельные
  пронумерованные источники со своими ссылками — иначе цитата в ответе перестанет совпадать с
  реально процитированным текстом.
- **Парсер — один движок с профилем на документ.** Грамматика «раздел → пункт» плавает между
  документами корпуса (нумерация, приложения, двуязычные шапки, сканы), но общих паттернов
  больше, чем уникальных: универсальный парсер + декларативный профиль на документ вместо
  отдельного скрипта на каждый тип нормы.
- **Coverage — метрика приёмки разбора PDF, а не факт «разобран».** Часть документов теряла
  55–80% нормативного текста: парсер по умолчанию отрезал всё после первого слова
  «ПРИЛОЖЕНИЕ», а у части документов серии EN нормативные требования продолжаются именно в
  приложениях. После доработки парсера доля текста, попавшая в структуру, выросла с 0.21–0.45
  до 0.71–0.80 у пострадавших документов; документы ниже порога уходят в карантин на
  доработку, а не заливаются в корпус с дырой. См.
  [`snippets/appendix_coverage.py`](snippets/appendix_coverage.py).
- **Гонка при параллельной записи — найдена и закрыта тестом.** Несколько процессов эвала
  одновременно писали общий кэш поверх файла, и чтение недописанного файла возвращало пустой
  словарь, который затем сохранялся поверх всего — кэш просел с 643 до 82 записей. Починено
  файловой блокировкой, слиянием с диском перед записью и атомарной заменой; добавлен
  регрессионный тест.

## Как меряем качество (эвал)

Прод не меняется по «стало субъективно лучше» — есть отдельный контур измерения:

1. **Генератор вопросов из корпуса.** По каждому пункту документа строится вопрос с «золотой
   цитатой» — дословным фрагментом нормы, где лежит ответ.
2. **LLM-судья по золотой цитате** (не по правдоподобию) — сравнивает ответ системы именно с
   этим фрагментом: `correct` / `partial` / `wrong` / `abstain`. Промахи и часть верных
   ответов дополнительно пересуживаются тремя голосами вместо одного — на пересуде 18% ранее
   ошибочных вердиктов меняются на `correct`, что и обосновывает пересуд как отдельный шаг, а
   не разовую проверку.
3. **Порог принятия гипотезы формулируется ДО замера**, а не после того, как видны цифры —
   письменно в журнале экспериментов, отдельно для «дешёвого» этапа без LLM (метрики поиска)
   и «дорогого» этапа с генерацией ответов.
4. **Итог по журналу:** из четырёх проверенных гипотез генерации/поиска (мягкий подъём
   релевантности по документу, укороченный контекст для реранкера, лексический поиск по
   переформулированным запросам, цитата в начале ответа) ни одна не перенесла выигрыш в
   промежуточной метрике поиска в выигрыш на эвале ответов — реранкер видит весь пул целиком и
   может взять нужный пункт независимо от его места в списке. Все остались за выключенным по
   умолчанию флагом: движок дисциплинированно не тащит в прод то, что не доказало пользу на
   измерении, даже если промежуточная цифра выросла.

**Текущие цифры производственного корпуса** (по журналу эвала):
корпус — 400 документов / 96 396 индексированных фрагментов; на сгенерированной по корпусу
линейке вопросов документ засчитывается «отвечает на отлично», если система верно отвечает
на все вопросы по нему — **214 из 400** документов; по всем 1952 вопросам линейки строгая
доля `correct` — **90,1%** (90,2% с зачётом равноценной по смыслу соседней нормы); попадание
верного пункта в пул кандидатов перед реранком — **~93%**.

## Архитектура

```
PDF (СП/СН/ГОСТ/EN)
   │
   ▼
universal parser (профиль на документ) ──▶ appendix parser (таблицы + проза)
   │                                              │
   └──────────────── coverage ≥ порога? ──────────┘
                        │ нет → карантин, доработка парсера
                        │ да
                        ▼
              index: эмбеддинги + BM25 (Postgres/pgvector)
                        │
Вопрос инженера ──▶ hybrid search (vector + BM25 + label, RRF)
                        │
                        ▼
                 LLM-реранк (AUX-тир, precision)
                        │
                        ▼
        + соседние пункты, + пункты парной нормы (СН↔СП)
                        │
                        ▼
        generate: ответ с тегами [И1]…[Иn] (GENERATION-тир)
                        │
                        ▼
        citation guard (теги в диапазоне?) + entailment (числа сошлись?)
                │пройдено                    │нет → доп. раунд поиска / отказ
                ▼
        ответ + «документ → пункт → страница», либо отказ

  ┄┄┄ отдельно, не в проде без порога ┄┄┄
  генератор вопросов из корпуса ──▶ прогон бота ──▶ LLM-судья по золотой цитате
        ──▶ пересуд промахов ×3 ──▶ журнал: гипотеза → порог до замера → флаг/отклонено
```

Подробнее, включая слоистую схему и контур эвала отдельными диаграммами —
[`docs/architecture.md`](docs/architecture.md).

## Стек

Python · Anthropic / OpenAI API (тот же провайдер-агностичный LLM-слой с тирами
SMALL/AUX/GENERATION, что и в предшествующем кейсе — см. ниже) · Postgres + pgvector
(векторный + лексический поиск в одной базе) · pypdf / pdfplumber (разбор PDF и таблиц) ·
Telegram-бот как интерфейс инженера · pytest (сотни офлайн-тестов парсера и логики
заземления).

**Связь с предыдущим кейсом.** Этот проект развивает
[`opz-generator`](https://github.com/Abasov11/opz-generator) — генератор инженерной
документации из того же портфолио: LLM-слой (`LLMProvider`, тиры моделей, учёт стоимости,
`FakeProvider` для офлайн-тестов) переиспользован без изменений бизнес-логики, а урок
«факты только из подтверждённого источника, форма — отдельно» здесь ужесточён до
тег-заземления и числовой сверки, потому что цена ошибки — не черновик документа, а прямая
ссылка инженеру.

## Статус

Действующий прод-ассистент (Telegram-бот), корпус и метрики растут итеративно под
управлением журнала эвала. Полная сборка, инфраструктура и данные заказчика в этот
публичный кейс не входят.
